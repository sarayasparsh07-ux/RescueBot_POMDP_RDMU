# Ground RescueBot's POMCP in exact beliefs

For a 4x4 RescueBot grid, the best practice is to run POMCP's search procedure (PO-UCT) with root states drawn from an **exact Bayesian belief**, and to rebuild the tree at every real step. This is not a shortcut. It is the setting in which Silver and Veness state their convergence theorem, and it removes particle deprivation, the failure mode particle POMCP is known for. Correctness then depends on a few details the paper's pseudocode leaves open: guarding UCB1 against zero visit counts, breaking ties at random, ending simulations at terminal states and at the real remaining horizon, and **scaling the exploration constant c to the return range**. That range is roughly 150 points or more for RescueBot's +100/−10/−50 rewards, so library defaults of √2 or 1.0 are badly mis-scaled, and any hand-tuned value should be reported as tuned and swept rather than presented as faithful to the paper. (c = 20 was an earlier candidate for this project; it was tested in the sweep but not selected.) Rollout policies that read the true victim location quietly erase the value of the Scan action, which is the thing POMCP should be demonstrating. That makes QMDP and MLS the natural baselines: by construction they place no value on information. (This project implemented and evaluated QMDP. MLS was not implemented; see the implementation note below.) For evaluation, run every policy on the same seeds (common random numbers) and compare per-seed differences. Report success rates with **Wilson intervals**, which stay informative at 50/50 successes where Wald collapses to a point, and report means with bootstrap intervals (BCa is SciPy's default; this project uses the percentile bootstrap with 5,000 resamples). Present one-factor-at-a-time sweeps as local and descriptive only.

> **Implementation status in this project (updated after the correction pass).** The statements below describe what `rescuebot_core.py` actually does; the rest of this note is the literature review that informed those choices.
>
> * **Root belief:** exact Bayes posterior over the 224 joint states (16 robot cells × 14 non-hazard survivor cells), with the tree rebuilt at every real decision (receding-horizon POMCP / PO-UCT).
> * **Rollout policy:** *belief-tracked*. Each rollout step chooses its move only from the exact posterior: target the most likely survivor cell, then take the move with the lowest expected hazard-aware cost-to-go over the robot-position belief, with 10% random moves. It then updates that posterior with the Bayes filter (predict, then condition on "survivor not reached"). The sampled hidden state is used only by the generative model, and the rollout never reads the sampled robot or survivor cell. The belief rollout never scans. Three rollout variants exist: `belief` (default, deployable), `random` (uniform-random baseline) and `oracle` (walks from the *sampled* robot cell to the *sampled* survivor cell; reads hidden state, so it is a non-deployable comparison only).
> * **Horizons:** the real mission limit is 30 decisions. The runner passes H_remaining = 30 − t at decision t. The configured tree depth is 10, so the effective tree depth is min(10, H_remaining). Rollouts stop at total depth H_remaining (depth already used inside the tree is counted), so no simulated reward is collected after the real deadline.
> * **Tree search details:** each history node has at most seven non-terminal successor histories: Up, Down, Left and Right each yield the single observation None, and Scan yields Cold, Warm or Hot. A rescue ends the simulation and creates no child. UCB1 is applied at every history node, with untried actions selected first. Ties are broken at random both in UCB selection and in the final root argmax over Q. Returns are backed up recursively (R = r + γ·R′, incremental mean). A rescue (terminal) transition returns its reward with no child node and no further simulation.
> * **Exploration constant:** c = 150, an empirically tuned, problem-specific setting rather than a universal constant. The pre-declared selection rule was the highest mean discounted return (the planner's own objective) in a sweep c ∈ {5, 20, 50, 100, 150, 300} on development seeds (base seed 77, 40 episodes per value). c = 150 had the highest mean discounted return (+6.8), but other metrics favour other values: c = 100 had the highest success-rate point estimate (90% vs 87.5%). c = 150 was **not** computed with Silver & Veness's R_hi − R_lo procedure (which uses runs with c = 0); its scale is merely broadly consistent with that reward-range guidance. c = 20 was an earlier candidate, tested and not selected. Reported results use separate evaluation seeds (base seed 2026).
> * **Initial survivor entropy:** the prior is uniform over the 13 admissible cells (14 non-hazard cells minus the known start), so H = log₂ 13 ≈ 3.70 bits, not 4 bits.
> * **Sensor and scan cost:** an imperfect, distance-banded Cold/Warm/Hot sensor (three Manhattan-distance bands: 0–1, 2–3, ≥ 4). Scan is free in the assignment model, because the slide specifies no scan penalty. An optional extension (notebook Section 13b) charges 2 points per scan.
> * **Episode counts:** main evaluation 100 episodes per policy; costed-scan extension 50 episodes per policy; sensitivity sweeps 40 episodes per point.
> * **Intervals actually computed:** Wilson 95% intervals for rescue success rates. Percentile-bootstrap 95% intervals (5,000 resamples, NumPy, fixed seed) for mean cumulative reward, mean discounted return and mean steps. For the paired comparisons, seed-matched paired percentile-bootstrap 95% intervals for differences in cumulative reward and discounted return, plus discordant rescue-outcome counts. Mean scans, mean hazard entries, hazard-entry rate, survivor MAP accuracy, final belief entropy and robot-location uncertainty are reported as point estimates **without** intervals.
> * **Baselines actually implemented:** risk-aware belief heuristic, QMDP, uniform random, and a clairvoyant value-iteration reference (non-deployable). **No standalone MLS policy was implemented or evaluated.** The risk-aware heuristic is *not* MLS. MLS acts on the single most likely joint state. The heuristic scans while its confidence is below 50% (at most two scans in a row), uses the most likely survivor cell only as a target, chooses moves by expected hazard-aware cost averaged over the whole robot-position belief, and charges hazard entries at their full penalty.
> * **Paired comparisons actually implemented** (notebook Section 13, `results/paired_comparisons.csv`): POMCP − heuristic and POMCP − QMDP, on the same 100 seed-matched episodes. Reported quantities are the mean per-episode differences in cumulative reward and in discounted return, with percentile-bootstrap 95% intervals, plus the counts of discordant rescue outcomes. No McNemar p-value is computed, and no multiplicity correction is applied.
> * **Recommended in this note but not implemented:** an MLS baseline; an expected-information-gain scanner; median or IQM reporting; correlation diagnostics across paired policy seeds; McNemar p-values; Bonferroni/Holm multiplicity corrections; BCa bootstrap intervals; and a two-factor sensitivity sweep (e.g. c × simulation count). These are disclosed methodological extensions, not completed experiments.

## Exact-belief PO-UCT is the paper's own baseline, not a shortcut

POMCP is UCT run over a tree of histories rather than states. Each simulation samples a start state from the root belief and descends by UCB1, V(ha) + c·√(log N(h)/N(ha)). When it reaches a history it has not seen, it expands every action child, evaluates the new leaf with a rollout, and backs up the discounted return as an incremental mean, V(ha) ← V(ha) + (R − V(ha))/N(ha). The real action is argmax V(ha) at the root ([Silver & Veness 2010](https://Www.Gwern.net/doc/reinforcement-learning/model/2010-silver.pdf)). The planner needs only a black-box generative simulator G(s,a) that returns (s′, o, r), not explicit probability tables ([Silver & Veness 2010](https://Www.Gwern.net/doc/reinforcement-learning/model/2010-silver.pdf)). Other reference implementations follow the same structure: expand all action children, evaluate leaves with random rollouts, and back up a running Q-average ([online-pomdp-planning PO-UCT](https://online-pomdp-planning.readthedocs.io/en/latest/methods/mcts/pouct.html)).

The paper first defines PO-UCT under the assumption that **the belief B(s,h) is known exactly**, with each simulation starting from a state sampled from B(·,h_t). The unweighted particle filter is introduced afterwards as the approximation that makes the method practical in huge state spaces. Theorem 1, which shows convergence in probability to the optimal value "for suitable choice of c", is stated for PO-UCT with the true belief ([Silver & Veness 2010](https://Www.Gwern.net/doc/reinforcement-learning/model/2010-silver.pdf)). pomdp_py uses the same split: "POMCP is POUCT plus a particle belief representation", and POUCT accepts any belief representation ([pomdp_py docs](https://h2r.github.io/pomdp-py/html/api/pomdp_py.algorithms.html)). RescueBot's joint state space has 16 robot cells × 14 non-hazard victim cells = **224 states** (hazard cells are excluded as victim locations). The initial victim prior covers only 13 of those 14 cells, because the known start cell is also excluded, so H(b_victim) = log₂ 13 ≈ 3.70 bits. An exact histogram filter over that space costs one small matrix product per step, so sampling root states from it is closer to the theory than particle POMCP is. It also avoids particle deprivation, which the paper concedes "is possible for large t" and patches by adding n/16 transformed particles after each real step ([Silver & Veness 2010](https://Www.Gwern.net/doc/reinforcement-learning/model/2010-silver.pdf)).

The accurate name for this design is "PO-UCT (POMCP's search) with an exact Bayesian belief, replanned online at every step". Replanning from the current belief each step and executing only the first action is the receding-horizon (MPC-style) pattern. No primary source in the notes uses "receding-horizon POMCP" as a standard term, so use the phrase descriptively. The original algorithm reuses the subtree that matches the real action and observation and prunes the rest ([Silver & Veness 2010](https://Www.Gwern.net/doc/reinforcement-learning/model/2010-silver.pdf)). With an exact root belief, reuse is optional. Rebuilding wastes the previous step's simulations but removes a whole class of bookkeeping bugs. If you do reuse the subtree, the root sampler must draw from the updated exact belief, not from particles stored in the subtree. Only the root needs the exact belief. Deeper nodes implicitly condition on the simulated histories that pass through them, which is correct under the paper's analysis.

## Five implementation traps decide whether the tree is correct

The published pseudocode has an off-by-one hazard. The expansion visit returns before the update lines, so on its next visit a new history has N(h) = 0 and every N(hb) = 0. That makes log N(h) and the bonus term undefined. The text also says "precisely one new node" is added per simulation while the pseudocode creates a child for every action, and the paper never reconciles the two ([Silver & Veness 2010](https://Www.Gwern.net/doc/reinforcement-learning/model/2010-silver.pdf)). UCT itself says nothing about unvisited arms beyond avoiding division by zero ([Kocsis & Szepesvári 2006](https://cs.nyu.edu/~shasha/papers/uct.pdf)). Libraries differ on initial counts: the paper and POMCP.jl default to N_init = 0 and V_init = 0, while pomdp_py defaults to num_visits_init = 1 ([POMCP.jl docs](https://juliapomdp.github.io/POMCP.jl/latest/solver); [pomdp_py docs](https://h2r.github.io/pomdp-py/html/api/pomdp_py.algorithms.html)). The robust rule is to give any action with N(ha) = 0 infinite priority, so each action is tried once before UCB1 takes over. With N_init = 1 and a small c, an untried action scoring 0 + c·√(log N) can be starved by a sibling whose value is near +100.

Terminal handling and horizons are the second and third traps. The paper cuts simulations when γ^depth < ε = 0.01 ([Silver & Veness 2010](https://Www.Gwern.net/doc/reinforcement-learning/model/2010-silver.pdf)). At γ = 0.95 that is about **90 steps**, much longer than RescueBot's 30-decision mission limit. The binding simulation limit is therefore the remaining mission horizon, H_remaining = 30 − t, while the POMCP tree itself is capped at a configurable depth of 10, so its effective depth is min(10, H_remaining). Otherwise simulated episodes run past the deadline and overvalue slow plans. Libraries add hard caps for the same reason: max_depth is 5 in pomdp_py, 20 in BasicPOMCP and 10 in POMCP.jl ([pomdp_py docs](https://h2r.github.io/pomdp-py/html/api/pomdp_py.algorithms.html); [BasicPOMCP docs](https://docs.juliahub.com/General/BasicPOMCP/stable/autodocs/); [POMCP.jl docs](https://juliapomdp.github.io/POMCP.jl/latest/solver)). None of the sources gives a terminal-state rule for PO-UCT. Standard practice is to return r with zero future value when G produces a terminal s′, in both SIMULATE and ROLLOUT, and not to create a child for it. Without this rule, post-rescue steps keep collecting −10 penalties or, worse, repeated +100 rewards. Discounting is recursive, R = r + γ·R_child, so V(ha) holds the return from that depth onward. Do not multiply by γ^depth a second time during backup.

The last two traps are action selection and the observation convention. SEARCH returns argmax_b V(hb), and UCT likewise returns the action with the highest average reward ([Silver & Veness 2010](https://Www.Gwern.net/doc/reinforcement-learning/model/2010-silver.pdf); [Kocsis & Szepesvári 2006](https://cs.nyu.edu/~shasha/papers/uct.pdf)). Choosing the most-visited child ("robust child") is a legitimate MCTS variant, but it is a deviation and should be labelled as one. No fetched source covers tie-breaking. The engineering point is that `numpy.argmax` returns the first maximum, which silently biases a grid agent toward whichever action is listed first, so break ties uniformly at random both inside UCB1 and in the final argmax. Finally, G must draw o from O(·|s′,a), the observation of the state after the action, and children should be keyed by the observation symbol (None/Cold/Warm/Hot).

The tree budget sets expectations, but the branching is smaller than a naive "5 actions × 4 observations" count suggests. RescueBot's observations are action-conditioned. The four moves each produce only the observation None, and Scan produces Cold, Warm or Hot. Each history node therefore has at most **seven** non-terminal action–observation successors, and a rescue transition creates no child at all. The planner runs 800 simulations per decision with a maximum configured tree depth of 10. How deep the tree is actually explored depends on visit frequencies, on which observations are reachable and on the budget, and rollouts evaluate outcomes beyond the tree. Actual depths and node counts should be quoted only when measured; the planner records `tree_nodes` and `max_depth_reached` for this purpose. Observation branching here is mild. Continuous observations make the tree collapse to a single layer and produce QMDP-like policies, a problem that POMCPOW and double progressive widening were built to address ([Sunberg & Kochenderfer, POMCPOW](https://arxiv.org/pdf/1709.06196v4)). Discretized POMCP did well on small discrete problems such as 1-D Light Dark ([POMCPOW](https://arxiv.org/pdf/1709.06196v4)). The convergence guarantees are asymptotic, with bias O(log N/N) ([Silver & Veness 2010](https://Www.Gwern.net/doc/reinforcement-learning/model/2010-silver.pdf)), so an 800-simulation planner is a heuristic whose quality must be shown empirically, not claimed.

## Exploration constant: reward-scale guidance and empirical tuning

**Theoretical guidance.** The paper's rule is explicit. Set **c = R_hi − R_lo**, where R_hi is the highest return seen in runs with c = 0 and R_lo is the lowest return seen in rollouts ([Silver & Veness 2010](https://Www.Gwern.net/doc/reinforcement-learning/model/2010-silver.pdf)). The rule uses returns, not single-step rewards. UCT's C_p = 1/√2, which recovers UCB1's √(2 ln t/s), assumes payoffs in [0,1] ([Kocsis & Szepesvári 2006](https://cs.nyu.edu/~shasha/papers/uct.pdf)). That is why pomdp_py defaults to √2 while noting that the POMCP paper used the reward range, and why BasicPOMCP and POMCP.jl default to c = 1.0 ([pomdp_py docs](https://h2r.github.io/pomdp-py/html/api/pomdp_py.algorithms.html); [BasicPOMCP docs](https://docs.juliahub.com/General/BasicPOMCP/stable/autodocs/)). Against ±100 rewards, a bonus of 1.0 is negligible and the search turns greedy after one visit per action.

**Applying the guidance to RescueBot.** RescueBot needs a flag here. A return range of at least 100 − (−50) = 150, and wider once several −10 steps or hazard entries accumulate, puts the paper-faithful c somewhere in the 100–200 range. A value of c ≈ 20 is about a tenth of that. It is not wrong: problem-specific tuning is the norm. POMCPOW's authors tuned c by cross-entropy to values such as 26 for Laser Tag and 110 for VDP Tag, and found that "performance appeared most sensitive to c" ([POMCPOW](https://arxiv.org/pdf/1709.06196v4)). Small action sets with shallow trees often do fine with less exploration. But any value of that order (c ≈ 20 was the initial suggestion here) must be described as tuned and backed by a sweep, for example c ∈ {5, 10, 20, 50, 100, 150}. This project ran such a sweep (plus c = 300) on development seeds and selected c = 150. The paper reports no per-domain numeric c, only the rule ([Silver & Veness 2010](https://Www.Gwern.net/doc/reinforcement-learning/model/2010-silver.pdf)), so the sweep is the evidence. An equivalent and cleaner option is to normalise returns to [0,1] using R_lo and R_hi and use c = √2. On the raw scale that equals about 1.4 × (R_hi − R_lo).

**Empirical tuning used in RescueBot.** The project did not run the paper's procedure (separate c = 0 runs to measure R_hi and R_lo). Instead, c was chosen by a pre-declared rule: the highest mean discounted return over c ∈ {5, 20, 50, 100, 150, 300} on development seeds (base seed 77, 40 episodes per value). That rule selected c = 150, which is the default in `rescuebot_core.DEFAULT_POMCP`. Its scale is broadly consistent with the reward-range guidance above, but it is an empirically tuned value, not one computed from R_hi − R_lo. It does not maximise every metric: c = 100 had a higher success-rate point estimate (90% vs 87.5%). The full sweep is reported in notebook Section 14, and all reported results use separate evaluation seeds (base seed 2026).

The rollout policy matters most when the tree is shallow. The baseline rollout picks uniformly among legal actions. The paper's domain-knowledge variant restricts rollouts to a "preferred" action set and initialises preferred actions optimistically (V_init = R_hi, N_init = 10) and all others pessimistically (V_init = R_lo). Rollout policies are formally history-based, π_rollout(h,·) ([Silver & Veness 2010](https://Www.Gwern.net/doc/reinforcement-learning/model/2010-silver.pdf)). State-based rollouts are common in practice. BasicPOMCP's FORollout runs them on the fully observable MDP ([BasicPOMCP docs](https://docs.juliahub.com/General/BasicPOMCP/stable/autodocs/)), and the POMCPOW authors credit a state-based rollout for POMCP doing much better on Laser Tag than earlier reports ([POMCPOW](https://arxiv.org/pdf/1709.06196v4)). In a search task, though, a rollout that walks straight to the true victim cell uses information the agent does not have. Leaf values then read as "victim location known", which distorts the value of Scan wherever rollouts, rather than the tree, supply the estimate. Prefer uniform-random rollouts, or a history-based heuristic that moves toward the hottest reading seen so far or toward the belief mode. If you use a state-based rollout, state its QMDP-like bias explicitly. (This project's default rollout is history-based: it carries the exact posterior forward step by step and chooses moves from it alone. The state-based variant is kept only as a labelled oracle comparison.) The notes found no study quantifying how much rollout choice matters on small grid-search POMDPs, so this is an analytical risk, not a measured effect.

## Predict-then-correct belief updates make entropy a trustworthy instrument

The exact update is the standard state estimator. Predict with b̄(s′) = Σ_s T(s′|s,a) b(s), then correct with b′(s′) = O(o|s′,a) b̄(s′) / Pr(o|b,a), where the normaliser Pr(o|b,a) = Σ_s′ O(o|s′,a) b̄(s′) ([Kaelbling, Littman & Cassandra 1998](https://axon.cs.byu.edu/~dan/778/papers/POMDP/cassandra.pdf); [Ross et al. 2008](https://arxiv.org/pdf/1401.3436)). The Bayes filter in robotics applies the motion update first and the measurement update second ([Probabilistic Robotics notes](https://calvinfeng.gitbook.io/probabilistic-robotics/basics/recursive-state-estimation/03-bayes-filters)), and Markov localisation uses the same cycle ([Fox, Burgard & Thrun 1998](https://project.dke.maastrichtuniversity.nl/swarmlab_old/wp-content/uploads/2012/07/fox98active.pdf)). Because the observation conditions on the post-action state, applying the observation to b(s) before the transition is a common bug. That ordering is valid only if RescueBot explicitly defines observations on the pre-action state. In matrix form:

```python
b_pred = b @ T[a]                 # predict
unnorm = b_pred * Z[a][:, o]      # correct
p_o = unnorm.sum()                # Pr(o | b, a)
if p_o <= 0: raise ImpossibleObservation(a, o)
b_new = unnorm / p_o
```

The zero-normaliser branch needs deliberate design. Pr(o|b,a) = 0 means every state with predicted mass assigns the observation zero likelihood. In a simulation where the simulator and the filter share one model, that can only be a bug: a wrong action index, a mismatched observation encoding, or a hard zero in the model. Raise an error there. Never reset silently to uniform, because a reset destroys information, makes entropy plots jump without explanation, and hides exactly the bugs that would invalidate a POMCP-versus-heuristic comparison. Even published code gets this branch wrong. One POMDPs.jl-style gist that intends to raise "INVALID BELIEF UPDATE" uses an assignment (`=`) where it means a comparison ([dressel gist](https://gist.github.com/dressel/b5f44535df5c4ca244e6b8f733184769)). If robustness is required, use a documented recovery instead: ε-smoothing of T and O, mixing in a small uniform component, or falling back to b̄. Count every fallback and report the count. Returning p_o from the update also gives the observation log-likelihood for free as a diagnostic.

Entropy H(b) = −Σ b(s) log₂ b(s), with 0 log 0 := 0, is the conventional uncertainty measure ([Cassandra, Kaelbling & Kurien 1996](https://cs.brown.edu/research/pubs/techreports/reports/96/cs96-17.pdf)). It is 0 for a point mass and maximal for a uniform belief ([Fox, Burgard & Thrun 1998](https://project.dke.maastrichtuniversity.nl/swarmlab_old/wp-content/uploads/2012/07/fox98active.pdf)). Cassandra et al. normalise it by the entropy of the uniform belief so that it lies in [0,1] ([Cassandra et al. 1996](https://cs.brown.edu/research/pubs/techreports/reports/96/cs96-17.pdf)). For RescueBot, the victim prior is uniform over the 13 admissible cells (non-hazard cells other than the known start), so its entropy is log₂ 13 ≈ 3.70 bits. A prior over all 16 cells would be exactly 4 bits. The dashboard should plot three quantities from the exact joint belief: H(robot) from the row sums, H(victim) from the column sums, and H(joint). The chain rule H(R,T) = H(R) + H(T|R) means a falling joint entropy can hide a rising robot-position entropy. Plotting all three also reveals the mutual information I(R;T) that arises when a "not detected" reading couples the two. Entropy is not monotone under exact updates: surprising readings and failed-move diffusion both raise it. A wobbling trace is therefore normal, while a jump to the maximum right after an observation points to a silent reset.

The term "robot localisation uncertainty" needs care when moves can fail and there is no odometry. The natural definition is entropy of the robot-position marginal, the convention Fox et al. use ([Fox, Burgard & Thrun 1998](https://project.dke.maastrichtuniversity.nl/swarmlab_old/wp-content/uploads/2012/07/fox98active.pdf)). Report it alongside the MAP confidence max_r b_R(r) and the belief mass on the true cell, which works as a calibration check in simulation. If no observation carries position information, this entropy can only hold steady or grow. The exceptions are wall collisions, which fold probability mass back onto edge cells, and indirect coupling through victim readings. Under those conditions "localisation" means tracking drift, not correcting it. Fox et al. saw a version of this: laser-only active sensing could not break corridor symmetry and did no better than random action selection ([Fox, Burgard & Thrun 1998](https://project.dke.maastrichtuniversity.nl/swarmlab_old/wp-content/uploads/2012/07/fox98active.pdf)). Standard benchmarks avoid the issue by making the robot's position fully observable, as in Tag, or known, as in RockSample ([Pineau et al. 2003](https://people.eecs.berkeley.edu/~russell/classes/cs294/s11/readings/Pineau+al:2003.pdf); [Ross et al. 2008](https://arxiv.org/pdf/1401.3436)). RescueBot should either do the same or add a position-informative observation, such as a bump or wall sensor, so that robot-position entropy becomes a metric the policy can actually improve.

## QMDP and MLS are the right foils because they ignore information value

The classic belief heuristics all come from Cassandra, Kaelbling & Kurien (1996). MLS executes the MDP-optimal action for the single most likely state. Voting weights each state's optimal action by b(s). QMDP picks argmax_a Σ_s b(s) Q_MDP(s,a), which "would be optimal if the agent's uncertainty existed for only a single step". Their entropy-based dual-mode controllers switch to uncertainty-reducing actions when the belief is diffuse ([Cassandra et al. 1996](https://cs.brown.edu/research/pubs/techreports/reports/96/cs96-17.pdf)). The defining weakness is well documented. QMDP "leads to policies that do not take actions to gain information" ([Kaelbling, Littman & Cassandra 1998](https://axon.cs.byu.edu/~dan/778/papers/POMDP/cassandra.pdf)) and is "not well suited for problems where explicit information gathering is required for success", although it is a cheap upper bound on the POMDP value ([Lauri, Hsu & Pajarinen 2022](https://arxiv.org/pdf/2209.10342)). In RescueBot, the MDP behind Q_MDP knows where the victim is, so Scan has only its cost there. QMDP and Voting will drift toward the weighted victim mass and never scan for information. That makes them the honest "zero information value" baseline. A one-step expected-information-gain scanner that switches to MLS once max b_T crosses a threshold is the matching "hand-coded information value" baseline. (This project's risk-aware heuristic is a simplified relative of that design. It scans on a confidence threshold rather than on expected information gain, and it moves by expected cost over the robot belief rather than by MLS.) Implementing all of them costs almost nothing once Q_MDP is available from value iteration: QMDP is the single product `argmax(b @ Q)`.

These heuristics are brittle, and the experiments should watch for their failure modes. In Cassandra's study with multiple start states, Voting, QMDP and the entropy methods scored **0.000** in one environment because they cycled without progress, while MLS stayed between 0.639 and 0.791. Under sensor noise, "QMDP failed universally" and never declared the goal ([Cassandra et al. 1996](https://cs.brown.edu/research/pubs/techreports/reports/96/cs96-17.pdf)). The entropy methods added little there because that domain had no explicit information-gathering action, which RescueBot's Scan does provide. Online and point-based planners beat these baselines clearly. On Tag, QMDP reached a 17% goal rate against 59% for PBVI ([Pineau et al. 2003](https://people.eecs.berkeley.edu/~russell/classes/cs294/s11/readings/Pineau+al:2003.pdf)). On RockSample(7,8), POMCP returned 20.71 against 9.46 for a plain rollout policy and 21.39 for offline SARSOP ([Silver & Veness 2010](https://Www.Gwern.net/doc/reinforcement-learning/model/2010-silver.pdf)), and a blind policy returned only 7.35 against 20.75 for AEMS2 ([Ross et al. 2008](https://arxiv.org/pdf/1401.3436)). No source compares MLS, QMDP and POMCP head-to-head on a grid-search task, so RescueBot's results will be its own evidence. Add a step cap and report the timeout rate, since cycling and failure to commit are the expected ways the baselines fail.

How sensing is priced determines whether POMCP has anything to show. In RockSample, Check actions carry no explicit reward, but their accuracy decays with distance, (1 + 2^(−d/d₀))/2, so moving closer buys better information ([Ross et al. 2008](https://arxiv.org/pdf/1401.3436)). Tiger's listen action has a small explicit cost ([Kaelbling, Littman & Cassandra 1998](https://axon.cs.byu.edu/~dan/778/papers/POMDP/cassandra.pdf)), and Tag charges −1 per move with γ = 0.95 ([TagPOMDPProblem.jl](https://docs.juliahub.com/General/TagPOMDPProblem/stable)). If RescueBot's Scan were free *and* perfectly informative, "scan, then follow MLS" would be close to optimal and much of POMCP's potential advantage would vanish. RescueBot's actual sensor is imperfect and distance-banded (Cold/Warm/Hot over three Manhattan-distance bands), so even a free scan still carries real information value. The assignment model keeps Scan free, because the slide specifies no penalty. A scan cost changes the incentive to gather information; this project tests that only as an optional extension (scan cost = 2, 50 episodes per policy, notebook Section 13b), alongside the unchanged 100-episode assignment evaluation. In that extension the observed rescue rates were POMCP 86%, risk-aware heuristic 76%, QMDP 0%, random 54% and the clairvoyant reference 100%. These are point estimates from a single 50-episode run. No paired significance test was performed for the extension, and no general guarantee that POMCP outperforms QMDP should be read into them.

## Paired seeds and Wilson intervals turn 100 episodes into evidence

For success rates and the rate of any hazard entry, use the Wilson score interval. Wald intervals collapse to zero width at 0/n or n/n and can cover as little as about 70% near the boundaries. Clopper-Pearson is valid but wide, and in one comparison it needed about 40% larger samples than the alternatives ([MetricGate](https://metricgate.com/blogs/wilson-vs-agresti-coull-vs-clopper-pearson/); [McGrath & Burke 2021](https://arxiv.org/pdf/2109.02516)). Brown, Cai & DasGupta recommend against Wald entirely and favour Wilson or Jeffreys at small n. That recommendation is reported via McGrath & Burke, who conclude that "the Wilson (score) interval provides the best overall performance" ([McGrath & Burke 2021](https://arxiv.org/pdf/2109.02516)). The case that matters for a strong planner is 50 successes out of 50. Wilson gives about **[0.929, 1.000]** where Wald gives [1, 1]. In code, call `binomtest(k, n).proportion_ci(method='wilson')`, because SciPy's default method is `'exact'` (Clopper-Pearson) ([SciPy docs](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats._result_classes.BinomTestResult.proportion_ci.html)).

For mean return, mean steps and mean hazard count, the *library default* in `scipy.stats.bootstrap` is BCa with 9,999 resamples. This is described here for reference; this project does not use it (see the note at the end of this paragraph). Pass `rng` for reproducibility, and fall back to the percentile method when BCa returns NaN on degenerate data, for example steps that are identical across episodes ([SciPy bootstrap docs](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.bootstrap.html)). Henderson et al. used 10,000 bootstrap iterations ([Henderson et al. 2018](https://arxiv.org/pdf/1709.06560)). Colas et al. warn against bootstrap tests below about 10 samples ([Colas et al. 2018](https://arxiv.org/pdf/1806.08295)), so 50–100 episodes is comfortably above that line. RescueBot returns will be bimodal (rescue versus timeout or hazard), so report the median or IQM alongside the mean, as Agarwal et al. recommend ([Agarwal et al. 2021](https://arxiv.org/pdf/2108.13264)). Report steps either conditional on success or together with the timeout rate, so that a policy that fails fast does not look efficient. *This project uses the percentile bootstrap with 5,000 resamples for reproducible interval estimation. No head-to-head comparison against BCa was conducted. Under the implemented method, constant-valued samples return a point interval. Median/IQM reporting was not implemented.*

Common random numbers do most of the statistical work. With paired runs, Var(mean difference) = (Var X + Var Y − 2 Cov)/n, so the gain depends on inducing positive covariance. The standard advice is to dedicate random numbers to each type of random event, so that the same draw serves the same purpose in every compared run, and to keep a policy's internal randomness from shifting those draws ([Haas, UMass CS590M](https://people.cs.umass.edu/~phaas/CS590M/slides/slecture11a.pdf); [Adan, TU/e](https://iadan.win.tue.nl/2S540/lecture7.pdf)). If POMCP's 800 simulations drew from the same generator as the environment, it would consume random numbers at a different rate from QMDP and the episodes would no longer be matched.

**How RescueBot implements this** (`rescuebot_core.py`):

1. **Separate seeds per episode.** `_episode_seeds(base_seed, i)` builds `np.random.SeedSequence([base_seed, i])` and spawns three child sequences, which become `env_seed`, `pol_seed` and `surv_seed`. They depend only on the base seed and the episode index *i*, never on the policy.
2. **Survivor location.** `_survivor_for_episode(config, surv_seed, survivor_mode)` draws the survivor uniformly from the 13 eligible cells (or uses the fixed (4,4) cell in `"fixed"` mode). Episode *i* therefore hides the survivor in the same cell for every policy.
3. **Pre-drawn environment randomness.** `RescueBotEnv.reset(env_seed)` creates `np.random.default_rng(env_seed)` and pre-draws two arrays of length `max_steps` (30): `_u_move` (movement success, compared with p = 0.8) and `_u_obs` (sensor noise). The step at decision *t* uses `_u_move[t]` and `_u_obs[t]`, so no policy's behaviour can change which numbers the environment uses.
4. **What is shared, and what is not.** For a matched episode, every policy faces the same survivor cell and the same sequence of uniform draws, indexed by decision number. The draws are shared, not the outcomes: when two policies take different actions or reach different cells, the same `_u_move[t]` or `_u_obs[t]` is applied to a different situation. Matching is therefore exact for the survivor location and partial for the move and sensor outcomes.
5. **Planner randomness is a separate stream.** `make_policy(spec, model, pol_seed)` seeds the policy. Inside `POMCPPlanner`, `SeedSequence(pol_seed).spawn(3)` gives three generators: one for root-state sampling and UCB/final-action tie-breaks, one for the simulated transitions and sensor noise inside the search (`u_sim`), and one for the rollout's ε-random moves (`u_pol`). None of them touches the environment's arrays. The Random baseline uses its own `default_rng(pol_seed)`. The risk-aware heuristic, QMDP and the clairvoyant reference use no random numbers: their actions are determined by the belief (or, for the clairvoyant reference, by the true state).
6. **Matched evaluation and paired differences.** `evaluate_policies` runs every policy over the same episode indices with the same `base_seed` (2026 for the main 100-episode evaluation). The notebook then pivots the per-episode results by `episode` and computes D_i = (POMCP outcome − comparator outcome) for each matched episode *i*, for cumulative reward and discounted return. The reported interval is a percentile bootstrap (5,000 resamples) of those D_i (`results/paired_comparisons.csv`). For success, it reports the discordant counts (episodes rescued by only one of the two policies).

The analysis then works on these per-seed differences. In general, use a paired-t or paired-bootstrap interval on D_i for continuous metrics, and McNemar's test or a paired bootstrap for success. (This project implements the paired bootstrap for reward and discounted return; for success it reports discordant counts without a McNemar p-value.) Overlapping marginal Wilson intervals are not a test, least of all under CRN, where the paired interval can be far narrower. Report the correlation between policies across seeds to show that CRN actually helped. Prefer effect sizes with intervals over p < 0.05 verdicts, publish per-episode results ([Agarwal et al. 2021](https://arxiv.org/pdf/2108.13264)), and apply Bonferroni or Holm corrections when several policies and metrics are compared ([Colas et al. 2018](https://arxiv.org/pdf/1806.08295)).

The table separates general recommended practice (from the literature above) from what RescueBot actually computes.

| Metric (per policy) | Recommended practice | Implemented in RescueBot |
|---|---|---|
| Success rate | Wilson 95%; McNemar or paired bootstrap vs. baseline | Wilson 95%. Paired: discordant rescue-outcome counts only (no McNemar p-value) |
| Any-hazard rate | Wilson 95%; McNemar | Point estimate only (no interval) |
| Mean cumulative reward | Bootstrap (BCa, ~10k resamples) plus median or IQM; paired-t or paired bootstrap on per-seed differences | Percentile bootstrap 95% (5,000 resamples). Paired percentile bootstrap for POMCP − heuristic and POMCP − QMDP. No median/IQM |
| Mean discounted return | As above | Percentile bootstrap 95% (5,000). Paired percentile bootstrap for the same two comparisons |
| Mean steps (with timeout rate) | Bootstrap; paired bootstrap | Percentile bootstrap 95% (5,000); no paired comparison |
| Mean hazard count | Bootstrap (skewed, zero-inflated); paired bootstrap | Point estimate only (no interval) |
| Multiple comparisons | Bonferroni or Holm | Not applied |
| CRN effectiveness | Report correlation between policies across seeds | Not computed |

Sensitivity sweeps over c, simulation count or sensor noise need honest framing. A one-factor-at-a-time design explores only a "hypercross" of the parameter space. In ten dimensions it leaves over 99.75% of the input space unexplored and cannot detect interactions, which is why Saltelli et al. call it "perfunctory, unless the model is proven to be linear" ([Saltelli et al.](https://arxiv.org/pdf/1711.11359)). It remains acceptable as a local, descriptive check around the nominal configuration if each sweep point carries its own interval and reuses the same seed list, so that the curve's shape reflects the parameter rather than seed noise. Two further disciplines matter. Picking the best c from a sweep and quoting its interval from the same episodes inflates the result (a winner's curse), so re-evaluate the chosen value on fresh seeds or label it exploratory. And where intervals overlap, write "no detectable sensitivity at n = X", not "insensitive". If you have time for one more experiment, a small two-factor grid over c and simulation count would address Saltelli's interaction critique.

## Conclusion

The main lesson is that on a problem this small, **the theory and the engineering point the same way**. The exact belief that is cheap to compute over RescueBot's 224 joint states (16 robot cells × 14 non-hazard survivor cells, with a 13-cell initial survivor prior) is also the belief Theorem 1 assumes. That shifts where the risk sits. The risk is no longer in belief approximation but in a handful of unspecified details: zero-count guards, terminal returns, horizon cut-offs and tie-breaking. These are the details most likely to separate a correct notebook from a plausible-looking one, so each deserves a unit test, for example that the belief sums to 1, that p_o is never 0, and that no reward accrues after rescue. The second lesson is that RescueBot's design decides what the experiment can show. POMCP's distinctive ability is valuing Scan beyond what QMDP sees. That requires an informative but imperfect sensor, which RescueBot's free, distance-banded scan already provides in the assignment model. It also requires rollouts that do not leak the victim's location, which is why the implemented rollout is belief-tracked. Costed scanning is studied separately as an optional extension. The planner works within a 30-decision mission limit, a maximum tree depth of 10 and a finite budget of 800 simulations per decision. Rollouts supply value estimates beyond the explored tree, so the rollout policy is a first-order design choice, not a detail. With a finite budget, POMCP's decisions are approximations: no global optimality is claimed.

The most persuasive evidence is not a headline success rate but the paired, seed-matched difference between POMCP and its baselines, shown with its interval, next to marginal entropy traces that show Scan actually reducing victim uncertainty. In this project the paired POMCP − heuristic and POMCP − QMDP differences are reported in the notebook (Section 13). The dashboard shows per-policy benchmark bars with marginal intervals and entropy traces, not the paired intervals. Report the chosen c openly as tuned (c = 150 here, chosen on development seeds), with a sweep and a held-out re-evaluation.

## Literature scope and remaining research questions

The following are limitations of *this literature review*, not missing features of the RescueBot implementation:

* The paper's own numeric c values per domain could not be found. Only the R_hi − R_lo rule is stated.
* No cited source gives an explicit terminal-state rule for PO-UCT. RescueBot implements the standard convention (return r, no child, no further simulation) and tests it.
* The Brown, Cai & DasGupta recommendations were read through a secondary source, not the primary text.
* No published head-to-head comparison of POMCP against MLS and QMDP on a grid-search task was found. RescueBot's own seed-matched results are the evidence for this specific problem, and they cover POMCP, QMDP and a risk-aware belief heuristic, not MLS.
